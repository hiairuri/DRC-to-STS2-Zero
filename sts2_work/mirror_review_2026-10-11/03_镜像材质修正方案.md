## 一、主轴：一条公式，两个缺失环节

01 §5.1 目标公式（真值，来源=运行时捕获 13 份 GLSL + 资产转储 + shader 重解码）：

```
out_sRGB = LinearToSrgb(  max(0, 1 − SrgbToLinear(albedo_sRGB))   ← 反相（t 恒 0）
                        + spec_direct + env_indirect×EnvBRDF )    ← 高光/环境（Phase 2）
           × 雾透射(=1) + 雾散射(=0)                              ← 中性，Phase 1 不动
```

即四步管线：**①sRGB 解码 → ②线性空间取反（t 恒 0）→ ③线性空间叠加高光（Phase 2）→ ④sRGB 编码**。
顺序不可颠倒（01 §5.1）。当前移植只有 ②：在 sRGB 空间直接取反，缺 ① 和 ④。

**主因量化**（01 §1.2 D1 / §5.3）：同一张图集，sRGB 域直取反 ≈0.35，线性取反再编码 ≈0.75，**差约 2 倍** ——与用户"太暗/发黑"的实测 0.35-0.39 精确吻合。反相本身不是 bug（02 §1 第 1 条：设计如此），**取反所在的色彩空间才是 bug**。

### 1.1 Godot 侧色彩空间裁定（方案关键前提，本轮新钉死）

01 §5.1 留了一个前提缺口："若引擎已解码则跳过①"。本轮用两条独立证据收敛：

1. **实测反推**：用户实测现输出 sRGB 均值 ≈0.35-0.39，与 01 §5.3「sRGB 空间直接取反」的理论预测 (0.35, 0.37, 0.39) **逐通道吻合**。若 Godot 管线在采样端硬件解码了 sRGB 纹理，现输出应为 ≈0.62（线性取反未编码）或 ≈0.75（解码+编码），均与实测不符 ⇒ **本管线 texture() 返回的是 sRGB 编码原值（未解码），COLOR 输出也不再被引擎二次编码，即端到端 sRGB 直通**。
2. **同项目旁证**：holo/dissolve 族 shader 的 `pipeline_encode = 0.0`，注释 "raw texture out (accepted look)"（`LingChar/pcksrc/drc_dye/profiles/ling/animations/characters/{ling,silent}/ling_holo_*.gdshader:50`、`ling_dissolve_mix.gdshader:31`）——同项目早已按"直通输出"交付并接受观感，与推断一致。

**裁定**：Phase 1 必须在 shader 内**同时补 ①解码 和 ④编码**，两者成对出现、缺一即偏。Godot canvas_item 着色器内手工实现 sRGB OETF 即可，无需动引擎设置。

## 二、Phase 1（必做，零猜值，全部参数有实锤来源）

### 2.1 公式改法（四个 gdshader 全部同步改）

**改动对象**（4 份，四族全改；虽然 02 §2.3 实测 50 槽 blend 全 normal、当前只有 mix 家族在画，但四族同步防未来 blend 变化踩坑，02 §2.3 同样建议）：

- `D:\ModForge\spikes\MirrorPupil\pcksrc\effects\mirror\ling_mirror_mix.gdshader`
- 同目录 `ling_mirror_add.gdshader` / `ling_mirror_mul.gdshader` / `ling_mirror_sub.gdshader`

**旧公式原文**（02 §2.1；本轮已对磁盘复核逐字一致，mix 为 `:43-51`，add/mul/sub 为各自 `:16-22`）：

```glsl
void fragment() {
	vec4 base = texture(TEXTURE, UV);
	// v37：mix(1−albedo, 0, t)
	vec3 inv = mix(vec3(1.0) - base.rgb, vec3(0.0), reveal);
	vec3 rgb = ambient_add + light_w * (inv + vec3(sheen));
	// h41：clamp(albedo.a × COLOR0.a)
	float a = clamp(base.a * v_col.a, 0.0, 1.0);
	COLOR = vec4(rgb, a);
}
```

**新公式**（对齐 01 §5.1 目标公式 + UE4 FS 最终合成顺序 `out = (高光+环境+反相)×雾.w + 雾.xyz` 再整体编码，01 §2.4b：182-201）：

```glsl
// —— sRGB OETF 标准实现（IEC 61966-2-1；与 UE4 运行时捕获的 LinearToSrgb 同构，
//    01 §2.4c：v33 = pow(c, InvGamma); out = min(c*12.92, pow(max(c,0.00313067), 1/2.4)*1.055−0.055)）——
vec3 srgb_to_linear(vec3 c) {
	bvec3 hi = greaterThan(c, vec3(0.04045));
	return mix(c / 12.92, pow((c + 0.055) / 1.055, vec3(2.4)), vec3(hi));
}
vec3 linear_to_srgb(vec3 c) {
	c = max(c, vec3(0.0));
	bvec3 lo = lessThanEqual(c, vec3(0.0031308));
	return mix(c * 12.92, pow(c, vec3(1.0 / 2.4)) * 1.055 - 0.055, vec3(lo));
}

void fragment() {
	vec4 base = texture(TEXTURE, UV);
	// ① 解码：图集是 sRGB 编码图像，本管线 texture() 不解码（本轮 §1.1 裁定）
	vec3 L = srgb_to_linear(base.rgb);
	// ② v37：mix(1−albedo, 0, t)，t=reveal 恒 0（darkenmpc.uexp MaxDarkenAlpha=0.0，01 §2.3）
	vec3 inv = mix(vec3(1.0) - L, vec3(0.0), reveal);
	// ③ spec/env 平面合成（Phase 1 保持中性 0；sheen 为线性域值）
	// ④ UE4 合成序：先线性域乘雾/加雾，再整体 sRGB 编码（01 §2.4b:271-278）
	vec3 lin = (inv + vec3(sheen)) * light_w + ambient_add;
	vec3 rgb = linear_to_srgb(lin);
	// h41：clamp(albedo.a × COLOR0.a)（01 §5.2 #19，不动）
	float a = clamp(base.a * v_col.a, 0.0, 1.0);
	COLOR = vec4(rgb, a);
}
```

要点：

- 两个转换函数用分支实现（`bvec3` + `mix`），线性段 12.92 / 幂段 1.055·x^(1/2.4)−0.055，与 UE4 捕获实码同构（01 §2.4c）。解码阈值取 0.04045（=12.92×0.0031308），编码阈值取 0.0031308，两函数互为逆。
- `linear_to_srgb` 前先 `max(c, 0)`：`inv + sheen ≥ 0` 恒成立（L∈[0,1]），但 pow 对负数未定义，防御性钳位与 UE4 的 `max(v37, 0)` 语义一致。
- **alpha 路径保持 `clamp(base.a * v_col.a)` 不变**（01 §5.2 #19 实锤）；**v_col.rgb 仍然丢弃不乘**（01 §5.2 #20：源 FS 顶点色 rgb 不参与；且 02 §2.6 警告：一旦改乘 rgb，`HitFlash.cs:37` 的 `/ling/` 过滤会让镜像跟着本体一起爆白闪——**Phase 1 明确不碰**，A4 改点不做）。
- **四族全部同步改**。add/mul/sub 三份的片元函数体与 mix 逐字相同（仅 render_mode 不同），新函数体可直接复制；mix 的头注 `:1-28` 需一并改写（见 2.2）。

## 三、Phase 2（暂缓，待 Phase 1 用户验收后决策，默认不实施）

Phase 1 落地后，观感 = 目标公式的"纯反相"项，均值 ≈0.71-0.77、p90≈0.98——**已经解决"太暗发黑"主诉（2 倍亮度差的唯一主因）**。真机还有的"高亮光影"来自 spec/env（01 §1.2 D2：DiffuseColor=0 ⇒ 高光+环境反射是唯一光影来源），Phase 2 才补这一项。两个子选项：

### 2a. 离线近似：常数线性 sheen（或 Fresnel 形状）

- **做法**：把 `sheen` 默认值从 0 改为线性域 ≈0.10（01 §5.3 量级参考第三行：叠加后 sRGB 暗部提升 +0.06~0.10）。纯 uniform 默认值改动，同样只需重打包。
- **合规性**：0.10 是**近似值、无运行时真值**（01 §5.2 #11/#12/#13：DirectionalLightColor、SpecularScale、环境立方图全部未确证，关卡+时段相关）。若用户接受"观感验收"口径（铁律 1 不禁止观感对齐，只禁止截图反解取证口径），即合规；但需在 commit/文档里如实标注"近似值，来源=01 §5.3 量级参考，非运行时实值"。
- **风险**：真机"光影"有空间结构（EnvBRDF 掠射角 5.2× 边缘增亮 + 方向光 GGX），2D 平面上 NoV 恒 ≈1（EnvBRDF≈0.0296，是**最小值端**），常数 sheen 是全画面均匀提亮，**给不出"边缘更亮"的空间分布**；若用 UV/alpha 边缘距离伪造 rim，就是凭空发明参数（违反铁律 1）。方向光色/环境立方图关卡相关，近似可能与真机有可见偏差。
- **成本**：≈0（改一个默认值+重打包+进游戏看一眼）。

### 2b. 先 hook 拿真值再实施

- **做法**：执行 01 §4.2 的 **H1**（glshim 垫片 hook `glShaderSource`，按特征串过滤抓镜像材质本体的运行时 FS 源码——确认 LinearToSrgb 尾巴与 pc3/pc5/pc6 槽位实值）+ **H5**（hook `glTexImage2D`/`glCompressedTexImage2D` 的 internalformat，验 `GL_SRGB8_ALPHA8`/ASTC sRGB 变体——闭合"输入解码"推断链）。
- **产出**：方向光色/SpecularScale/InvGamma/preExposure 等可溯源实值（01 §4.1 未确证清单大部分闭环），Phase 2 参数全部有实锤。
- **成本**：需用户配合跑游戏做捕获（装 glshim 垫片、复现战斗场景、回收捕获文件）；UE4 侧是手游包，还需要运行环境。
- **铁律合规性**：最优（运行时真值，零猜测）。

### 给主控的建议

**推荐：先 2a 观感验收，不满意再 2b。** 理由：
1. Phase 1 已经拿掉 2 倍亮度主因，用户主诉大概率已解；2a 是零成本增量（改一个默认值），先用最小代价探"用户对光影量的容忍区间"；
2. 2b 的捕获链路要用户配合且不一定一次成功（H1 特征串过滤能否命中 spine 材质本体未验证；01 §4.1 自认"捕获到的都是 UI/后处理程序"），在用户还没确认 Phase 1 方向正确之前投入，性价比低；
3. 2a 失败的信息量也有价值：若常数 sheen 明显不像，说明"光影"的空间结构（边缘增亮）是主要观感特征，那 2b 就不是可选项而是必选项——届时再上 hook 拿方向光/立方图真值。
